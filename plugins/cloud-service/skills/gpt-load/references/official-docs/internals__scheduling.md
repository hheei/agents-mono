# 调度是怎么做的

这一页讲内部机制。不了解也能正常使用，但排查「为什么走了这个凭据」时会很有用。

<div class="docs-rule">

</div>

<div class="prose">

## 一次请求的完整路径<a href="#flow" class="anchor" aria-label="复制本节链接">§</a>

请求进来之后，网关依次做这几件事：

1.  **认证**——校验访问密钥是否有效、是否被停用
2.  **协议检查**——这把密钥允许用当前协议吗
3.  **筛选分组**——在密钥授权的分组里，找出能提供该模型的
4.  **选凭据**——从候选分组中按路由策略和权重选择可用凭据
5.  **转发**——必要时做协议转换，发往上游
6.  **失败则重试**——换一个凭据再来，直到成功或用完次数

路由检查会说明访问密钥、分组或凭据为什么不能成为候选。 它的 `reason_code` 与客户端响应 `code`、 请求日志 `error_code` 是不同的信息，见本页最后一节。

## 候选分组<a href="#group" class="anchor" aria-label="复制本节链接">§</a>

候选分组要同时满足：

- 在这把访问密钥的授权范围内
- 处于启用状态
- 已开放请求里的那个模型
- 有效权重大于 0

满足条件的分组共同提供候选凭据。同一个模型配置多个来源后，一个分组不可用时，其他分组仍可参与调度。

## 可用凭据<a href="#cred" class="anchor" aria-label="复制本节链接">§</a>

继续筛选这些分组中的凭据：

- 状态为可用（不是停用、冷却中、已拉黑）
- 订阅账号还需授权状态正常
- 有效权重大于 0

网关按当前路由策略，在可用候选中按「分组权重 × 凭据权重」加权轮询。 请求亲和仍可优先复用之前成功的凭据，实际流量不保证严格按权重分配。

## 权重<a href="#weight" class="anchor" aria-label="复制本节链接">§</a>

分组和凭据权重默认均为 50，可设置为 1–100；数值越大，相对获得的流量越多，不再根据成功率自动计算。

<div class="notice notice-blue">

<span class="t">暂停流量请使用停用</span>

当前管理台和管理 API 都不接受手动权重 0。 需要暂时停止流量时，请停用对应分组或凭据；配置和历史统计仍会保留。

</div>

## 会话亲和<a href="#affinity" class="anchor" aria-label="复制本节链接">§</a>

开启后，网关会根据访问密钥、客户端协议以及请求中的指令或首个用户输入前缀 生成软亲和键。具有相同稳定前缀的后续请求，会优先复用之前成功的凭据。

Chat Completions 与 Responses 也可通过有效的 prompt_cache_key 形成软亲和，但亲和命中不代表上游缓存必然命中。 Responses 的响应 ID 续接独立于软亲和，边界见协议页。

[查看 Responses 续接边界 →](/docs/internals/protocols#stateful)

亲和记录有 TTL 和容量上限（默认记一万条），超出后按老旧程度淘汰。**亲和不是绝对的**：如果记住的那个凭据已经冷却或拉黑， 网关仍会换一个可用的，保证请求能发出去。

参数配置见 [运行时设置](/docs/settings)。

## 失败之后<a href="#retry" class="anchor" aria-label="复制本节链接">§</a>

安全允许重放时，网关可换候选重试；额外重试次数由全局设置决定，跨分组切换也共用同一预算。

关键在于「什么算失败」：

- **会重试**——上游限流、服务端错误、网络超时这类**换个凭据可能就好**的问题
- **不重试**——明确的参数错误、上下文超限或内容政策拒绝， 换凭据也一样失败，重试只是浪费时间

明确的模型或能力拒绝可在安全边界内切换候选；已经输出或执行结果未知时，不盲目重放。响应 ID 续接不会换用其他凭据。

<div class="notice notice-blue">

<span class="t">流式响应的特殊处理</span>

流式请求一旦开始输出，就**不能再重试了**—— 客户端已经收到前半段内容，换凭据重发会导致内容错乱。 所以网关只在**第一个数据块到达之前**做安全切换， 之后出错只能如实返回给客户端。

</div>

## 冷却与拉黑<a href="#cooldown" class="anchor" aria-label="复制本节链接">§</a>

两级保护机制，避免坏凭据反复拖慢请求：

- **冷却**——凭据出错后**暂时跳过**， 到点自动恢复。上游限流时最常见，属于正常现象
- **拉黑**——连续失败次数超过阈值后自动摘除；API Key 验活成功后可自动恢复，订阅凭据需人工处理

模型级限流只冷却该凭据的对应模型，其他模型仍可参与调度；明确的凭据级限制仍影响整份凭据。恢复凭据会清除其模型冷却。

区别在于：冷却是**临时避让**，假设问题会自己好； 拉黑是**判定这个凭据坏了**，比如密钥被吊销、账号欠费。

**成功一次就会重置连续失败计数**—— 偶发抖动不会累积到拉黑。

阈值配置见 [运行时设置](/docs/settings)， 当前状态在 [监控与排障](/docs/monitor) 的健康页看。

## 选不中时的原因码<a href="#reasons" class="anchor" aria-label="复制本节链接">§</a>

路由检查按访问密钥、分组和凭据返回分层 `reason_code`。 完整原因、所属层级和处理方式统一收录在错误参考页。
